One team installed the same QEN model on the same card for the same people.  With a user connected, it responded in seconds.  With 40 users connected at the same time. Response times went from 3 seconds to more than a minute.  Nobody touched the model.  What failed was what was behind it.  The server that distributes that GPU among everyone.  That's the real problem behind this video.   It's not that Quen is so fast, it's that he remains so fast even when he stops being just yours.  And the answer depends almost entirely on three pieces of software.  Llamaso FPP, VL M and Slang. Same GPU, same weights.  Three completely different ways of distributing that memory.  We're going to break down each one with figures you can verify yourself, not with your typical marketing chart. Llama cpp.  Let's start where almost everyone starts.  Yama.cpp is a single C++ binary, with no Python, no Kuda Tool Kit, and no long list of dependencies.  You point the server to a GGUF file and in seconds you have an OpenAI compatible endpoint on your own machine.  It runs on a laptop, on a Mac, on a Raspberry Pi, on an old CPU without a GPU.  That portability, not speed, is the reason it exists.   It's more than enough for one person.  A model the size of Quen in 4-bit takes up between 15 and 20 GB of Uber RAM depending on the exact variant and on a consumer card can deliver around 35 tokens per second, faster than most read.  Here comes the part that many videos exaggerate.  Ylam.  Cpppup does support multiple users at the same time.  It has internal lanes called slots and continuous batch processing has been enabled by default for a long time.  The problem is not that it only serves one person, it's that each slot reserves a fixed block of cache memory in advance, whether it's used or not.  In a test published this year on an A40 GPU, latency remained stable up to about eight simultaneous requests. After that point, it began to grow erratically because all the lanes were already occupied.  It's not that it collapses with the second person, it's that it doesn't scale much beyond a handful.  Oyama. Many people are aware of this limitation without knowing it because they feel it through Oyama.  Oyama is not a new engine; it's a Go layer that wraps Yama.cpp to make it easier to install and update.  That's why it inherits almost the same behavior.  By default, it processes requests in a queue.  one after the other, although it can be configured to accept several in parallel with an environment variable.  The problem is that this configuration does not reorganize the work with the intelligence of a real continuous batch processing.  So as more people join, the queue grows and the time until the first word starts to increase without any improvement in generation speed.  It's almost literally the case I opened this video with.  When that server stops being just for me and becomes for the whole team, the default candidate is ulem.  Its central idea is called paged attention.  Instead of reserving a large, fixed block of memory for each user, it divides it into small pages and delivers them only when a request actually needs them.  Just like the virtual memory of an operating system, no request hogs space it's not using, so many more people can fit on the same card at the same time.  In addition to that, there is continuous batch processing.  The instant one request finishes using a token, another that was waiting takes its place, and the GPU almost never stands still between steps.  BL LM also runs on almost any hardware.  Nvidia, AMD, Intel, TPU, Trainium, and Heid cards are supported, and the engine has the largest contributor community of the three engines, resulting in almost immediate support for new models as soon as they are released.  If your traffic is a mix of requests that don't look alike, or if your hardware isn't a standard Nvidia card, this is still the safest default option .  Now for the piece that gives this video its name.  Selangó is based on a 2024 study by the same Stanford Berkeley and LMCs group that created Chatbot Arena, and its central idea is RADX attention.  Instead of just recognizing a complete identical prefix as classic cao does, it stores each request it has seen within a prefix tree.  When a new one arrives, it goes through that tree.  It finds the longest branch that it already shares with something previous, reuses it at no cost, and only calculates the new one at the end.  This matters a great deal to how real agents work .  The same system message, the same list of tools, the same chat history with just a few new tokens each time.  In multi-turn conversations, that tree achieves cache hit rates of between 75 and 95%.  Depending on the case, Slang has a second, lesser-known trick.  When the response must follow a fixed scheme or format, Jason, as happens in almost any tool call, compiles that grammar into a state machine and decodes multiple tokens at once instead of one by one.  Without that technique, typical compliance with a Jason scheme ranges between 90 and 94%. With it, it goes up to a range of 96 to 98% with almost no extra time cost.
